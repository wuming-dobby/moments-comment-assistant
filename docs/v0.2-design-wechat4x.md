# 朋友圈助手 v0.2 设计方案：兼容微信 4.x（待审）

- 日期：2026-11-21
- 作者：Hermes（deepseek-flash）
- 审阅：DSH bots（主控／编码／复核）
- 结论先行：v0.1 在新电脑上「双击没反应、朋友圈无浮窗」，根因是**窗口类名写死成微信 3.x**，与电脑无关。

## 一、根因与证据

| 项 | 实测 |
|---|---|
| 本机微信进程 | `Weixin.exe`（4.x） |
| 微信主窗口类名 | `Qt51514QWindowIcon` |
| 代码写死类名 (`src/capture.py:10`) | `WeChatMainWndForPC`（微信 3.x） |
| 按旧逻辑命中窗口数 | **0** |
| 按进程名枚举命中 | 2 个可见顶层窗（面积 114848 / 97350） |

三个症状同一根因：

1. `poll()` 判 `wechat_is_foreground()` → `find_wechat_window()` 返回 `None` → 浮窗永不 `show()`（`src/overlay.py:11-16, 54-62`）。
2. 主窗为 `Qt.Tool`＋无边框、无托盘、无任务栏项，启动即隐藏 → 用户观感「双击没反应」（`src/overlay.py:24-33`）。
3. 点「生成评论」走同一函数 → 只弹「没找到微信窗口」（`src/main.py:23-27`）。

附带两处必须一并修的隐患：

- 配置路径 `Path(__file__).parents[1]/config.json`（`src/vision.py:9`）：onefile 打包后落在 `_MEIPASS` 临时目录，**关掉即丢**，每次启动都要重配。
- 截图用 GDI `GetDC(0)+BitBlt`（`src/capture.py:40-46`）：微信 4.x 走 Qt＋硬件合成，极易截到全黑图；草稿会基于黑图瞎编。

## 二、改动清单（六项）

### F1 窗口识别：按进程名，不认死类名

- 位置：`src/capture.py`
- 做法：`EnumWindows` 后按 `GetWindowThreadProcessId` → `QueryFullProcessImageNameW` 取进程名，命中 `{weixin.exe, wechat.exe}` 且 `IsWindowVisible` 的顶层窗；取 `GetWindowRect` 面积最大者。
- 兼容：类名白名单 `{WeChatMainWndForPC, Qt51514QWindowIcon}` 仍保留作快路径，但**不再作为唯一判据**。
- 性能：结果缓存 2 秒；每轮 `IsWindow(hwnd)` 校验，失效即重查。

### F2 前台判定：只要前台窗属于微信进程

- 位置：`src/overlay.py:11-16`
- 做法：`GetForegroundWindow()` → 取其进程名 ∈ 微信进程集合 → 视为微信在前台；`IsIconic` 仍判 False。
- 效果：朋友圈是 4.x 内的独立窗，用它判断也能让浮窗出现（v0.1 只比主窗句柄，永远不等）。

### F3 托盘图标 + 常显开关（解决"没反应"观感）

- 位置：`src/main.py`、`src/overlay.py`
- 做法：`QSystemTrayIcon`（图标复用 exe 图标），菜单三项：`显示浮窗 / 设置 API… / 退出`；左键单击显示浮窗 3 秒。
- 新增开关「常显浮窗」（托盘勾选，记进 config）：默认仍跟随微信前台，勾选后不随前台变化隐藏，便于调试与投屏演示。

### F4 配置与日志落到 `%APPDATA%`

- 位置：`src/vision.py:9`、新增 `src/paths.py`
- 做法：`%APPDATA%\MomentsAssistant\config.json`；旧路径、`VL_*` 环境变量仍读，优先级：环境变量 > `%APPDATA%` > 旧 `config.json`。
- 日志：`%APPDATA%\MomentsAssistant\app.log`，1 MB × 3 轮转；启动、窗口查找结果、API 耗时、异常 traceback 各记一行。
- 新增 `--debug`：控制台模式打印同样内容（另出一个 console 版 exe，可删）。

### F5 截图：PrintWindow 优先，黑图检测，再降级

- 位置：`src/capture.py:36-`
- 做法：
  1. `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)`；
  2. 采样中心 5×5 像素，若平均亮度 < 8/255 或方差 < 2 → 判黑图；
  3. 降级 `GetDC(0)+BitBlt`；仍黑 → 抛出明确异常「微信 4.x 截图失败，请改用剪贴板模式」；
  4. DPI 由 `SetProcessDPIAware()` 升到 `SetProcessDpiAwarenessContext(PerMonitorV2)`（`src/main.py:41`）。
- **F5 兜底（同时做，独立于截图技术）**：浮窗加「用剪贴板图片」按钮——用户 `Win+Shift+S` 或微信自带截图后，一键从剪贴板取图生成草稿。这条让功能不押在 PrintWindow 是否能截 4.x 上。

### F6 单实例与启动反馈

- 做法：命名互斥体 `Global\MomentsAssistant_v2`；第二实例把已有浮窗顶到前台并退出。
- 启动 3 秒内无窗口时，托盘气泡提示「已在后台运行，微信前台时显示浮窗」，避免再次误判"没反应"。

## 三、接口与契约（不变的部分）

- 模型接口仍走 OpenAI 兼容 `chat.completions`，配置三项 `VL_API_BASE / VL_API_KEY / VL_MODEL`。
- 输出仍只写剪贴板，**不自动发送、不注入、不读取微信数据库**（红线不变）。
- 不改打包形态：PyInstaller onefile、`--noconsole`、arm64 无关（x64）。

## 六、风险与非目标

- **风险 R1**：PrintWindow 在 4.x 仍可能全黑（DirectComposition）。缓解＝F5 兜底剪贴板模式；不为此引入 winrt/WGC 重依赖（v0.3 再议）。
- **风险 R2**：微信进程改名（如 `WeChat.exe` 国际版）。缓解＝进程名集合可配置，config 里给 `wechat_procs` 字段。
- **非目标**：不做自动发送、不做多开、不做手机端、不改 UI 风格、不动模型侧提示词。
